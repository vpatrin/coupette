# Migrations

> Read whenever modifying SQLAlchemy models in `core/` or anything under Alembic.

## Hard rules

1. **Model is the source of truth.** Indexes, constraints, columns — all defined on the SQLAlchemy model in `core/`. Migrations are patches for existing databases, not the schema definition.
2. **Generate, never hand-write.** `make revision` needs `docker run`, which the crew's sandbox blocks. Generate against this worktree's throwaway database instead, once it is at head (`make migrate` from the worker setup):

   ```bash
   set -a; . ./.env.local; set +a
   (cd core && DATABASE_URL= poetry run alembic revision --autogenerate -m "<descriptive>")
   make format
   ```

   `.env.local` comes from `exp-docker db up`, so the DB is this worktree's own. Blanking `DATABASE_URL` keeps alembic on those `DB_*` values.
3. **Migrations run only against this worktree's throwaway DB.** `make migrate` and any `alembic upgrade`/`downgrade` are allowed only after `~/.agent-harness/bin/exp-docker db up > .env.local` ran in this worktree and `grep -q '^DB_PORT=' .env.local` succeeds. Without it, the shared `.env` defaults point at slot 0, which belongs to another worktree. Never `make dev`. Need a clean DB? `exp-docker db reset`, then `make migrate`.
4. **Forward-only in production.** `downgrade()` stays as autogenerated and is never run in prod. Fix a mistake with a new migration.
5. **Risky changes need two steps:**
   - NOT NULL on existing column? Add nullable + backfill, then alter to NOT NULL
   - Large-table index? Use `postgresql_concurrently=True` for `CREATE INDEX CONCURRENTLY`
   - Renaming a column? `ALTER TABLE ... RENAME COLUMN`, not drop+add

## Workflow

1. Modify the SQLAlchemy model in `core/`
2. Generate the revision as in rule 2
3. Read the generated file in `core/alembic/versions/` — autogenerate gets constraint names and `server_default` subtly wrong. Fix the model and regenerate rather than editing the file. Exception — operations autogenerate can't express (column rename, data migration, `CONCURRENTLY` index): edit the generated file, keep its header, and record the edit in the commit body.
4. Record backfill needs, lock risk, or a two-step plan in the commit body and the journal's Decisions line. `/code-review` reads the generated file. Nothing applies it to production: `exp/agentic` never deploys.

`docs/DEVELOPMENT.md#migrations` describes the main lane (shared DB, `make own-db`, `make revision`). In this lane, this rule wins.
