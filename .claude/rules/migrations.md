# Migrations

> Read whenever modifying SQLAlchemy models in `core/` or anything under Alembic.

## Hard rules

1. **Model is the source of truth.** Indexes, constraints, columns — all defined on the SQLAlchemy model in `core/`. Migrations are patches for existing databases, not the schema definition.
2. **Generate, never hand-write.** `make revision msg="<descriptive>"` is codegen against an ephemeral `coupette-revision-tmp` Postgres on `127.0.0.1:5433`: it replays the existing migrations, autogenerates, removes the container, then runs `make format`. It blanks `DATABASE_URL` so the replay can't reach a real database, so you run it yourself. Before the first run in a session, read the `revision` target in the `Makefile`; if it no longer matches this description, stop and ask Victor. The container name and port are fixed: one `make revision` at a time across workspaces, and an interrupted run may leave the container behind (`docker rm -f coupette-revision-tmp`).
3. **`make migrate` is never yours.** It runs `alembic upgrade head` on a real database and creates the admin user. Victor runs it, always — same for any `alembic upgrade`/`downgrade` against a real DB.
4. **Forward-only in production.** `downgrade()` stays as autogenerated and is never run in prod. Fix a mistake with a new migration.
5. **Risky changes need two steps:**
   - NOT NULL on existing column? Add nullable + backfill, then alter to NOT NULL
   - Large-table index? Use `postgresql_concurrently=True` for `CREATE INDEX CONCURRENTLY`
   - Renaming a column? `ALTER TABLE ... RENAME COLUMN`, not drop+add

## Workflow

1. Modify the SQLAlchemy model in `core/`
2. Run `make revision msg="..."` (needs Docker)
3. Read the generated file in `core/alembic/versions/` — autogenerate gets constraint names and `server_default` subtly wrong. Fix the model and regenerate rather than editing the file. Exception — operations autogenerate can't express (column rename, data migration, `CONCURRENTLY` index): edit the generated file, keep its header, and record the edit in the PR's Decisions.
4. Record backfill needs, lock risk, or a two-step plan in the PR's Decisions section. Victor reviews the generated file in the PR diff and applies it at deploy time.

See `docs/DEVELOPMENT.md#migrations` for full practices.
